### 1. Bonsai 2 is Qwen3.8-derived — and the GGUF arch string will mislead you

**Corrected mid-session: I read `general.architecture = qwen35` from the GGUF and concluded
Qwen3.5. That was wrong.** That field and `tokenizer.ggml.pre` are **llama.cpp code-path labels**
— which kernel and pre-tokenizer regex to use — not provenance. llama.cpp runs newer models on
an existing handler.

**The fingerprint that settles it: vocab 248,320 tokens.** Qwen3/3.5 use ~151,936. The vendor's
parameter split confirms it: 2.54B embedding/LM head = 248,320 x 5120 x 2.

From the GGUF and PrismML's documentation together:

- **Qwen3.8-27B base**, PrismML ternary compression, {-1,0,+1} with FP16 group scales,
  ~1.76 effective bits/weight; 98.2% of the FP16 baseline at ~1/9 the size.
- Hybrid attention **~75% linear / ~25% full** (GatedDeltaNet) — in the GGUF that is
  `full_attention_interval = 4` and the `ssm.*` keys, which carry GatedDeltaNet parameters
  because the shapes match. **It is not Mamba.**
- `block_count 65` = 64 language blocks + 1 MTP layer; hidden 5120; 24 heads / 4 KV heads;
  262,144 context; **multimodal — 0.47B vision tower, it accepts images** (previously unrecorded).
- MTP drafter is genuine (`--spec-type draft-mtp`, `nextn_predict_layers 1`), so **existing
  Qwen3.8 tokenizer and speculative-decoding work carries over directly** — it is not Qwen3.5 work.

Note the served file is `bonsai2_mtp/bonsai2-mtp-q8.gguf`, not the PQ2_0 pack the 2026-09-21
entry describes; `run_bonsai_p100.sh` defaults to `SPEC=draft-mtp`.

**Architecture does not solve the context problem.** GatedDeltaNet plus sparse full attention cut
the *memory* cost of 262K context — which is why it fits in 14.9 GB — but every token of a 40k
prompt is still prefilled once through 64 blocks. No attention scheme makes the first pass free.
Context management stays the harness's job.

### 1. BIOS writes over SSH now WORK — `hp-repsetup`, not `hp_bioscfg`

Installed **HP Flash and Replicated Setup Utilities for Linux v3.26** (SoftPaq `sp171387`,
released 2026-03-05) plus **`hpuefi-mod` 3.07**, from `ftp.hp.com/pub/caps-softpaq/cmit/linuxtools/`.
A local copy of the tarball is staged; the tree is on the box at `~/hptools/`.

- **`hpuefi.ko` COMPILES AND LOADS on kernel 7.0.0-31-generic.** HP's `hpuefi-vm-flags.sh` helper
  detects the live access mechanism and rewrites `hpuefi.c` from `hpuefi.c-template`, which is
  exactly the 6.3+/`VM_LOCKED`/`memdesc_flags` churn that broke older versions.
- **Secure Boot was already disabled** (`mokutil --sb-state`), which is a hard requirement — HP
  ships the module unsigned.
- Install: `make && sudo make install` in `hpuefi-mod-3.07/`, then `sudo ./install.sh` in
  `hp-flash-3.26_x86_64/`. The app installer requires the module to be in `/lib/modules`, not
  merely `insmod`-ed. Device node via `mkdevhpuefi` (it is a one-line `mknod` script, run with `sh`).
- Made persistent: `/etc/modules-load.d/hpuefi.conf` + `hpuefi-dev.service`.
  **Gotcha:** systemd does NOT expand `$(uname -r)` in `ExecStart` — hard-code the kernel path.
- Usage: `sudo /opt/hp/hp-flash/hp-repsetup -g -a <file>` to dump (667 lines ASCII),
  `-s -a <file>` to set. **Only fields present in the file are touched**, so always hand it a
  minimal file, never a full restore. `-a` avoids the UTF-16 editing hazard entirely. No BIOS
  password is set, so no `-p`.
- The in-tree `hp_bioscfg` driver is still write-dead (`0x4 "Invalid command type"`,
  `ACPI-package does not have enough elements: 11 < 13`). `hp-repsetup` bypasses it. **Reads via
  `hp_bioscfg` remain fine and are a useful independent check.**

### 2. CORRECTION — the black-screen root cause was WRONG

The recorded cause was `Configure Option ROM Launch Policy = All UEFI` vs the Quadro's legacy-only
Fermi VBIOS, fixed by `All UEFI Except Video`. **That is not what fixed it, and that write never
once succeeded** — it was rejected `(Invalid Parameter)` on both attempts.

would have been a black screen and a false negative.

### 9. SHROUD A/B — ducting is worth 2.4x runtime but is NOT sufficient alone at 150 W

Second run, same script, same guards (kill@70 C / poweroff@75 C), same model and config. The ONLY

| heating rate | 0.29 C/s | **0.21 C/s** |

Full run 2 series: 20.47@44, 19.81@48, 18.27@51, 18.46@54, 19.06@56, 18.36@59, 18.19@61, 17.92@63,
18.62@65, 17.49@67, 17.62@69 -> GUARD. Clean kill, **0 Xid**, idle 30 C at 25.3 W beforehand.

**20.47 t/s is the fastest figure ever recorded on this box**, above the 19.44 champion at 47 C —
because the cooler card held 1328 MHz instead of settling to the power-capped 1189 MHz.

**But it did NOT plateau.** The rate decelerated (0.36 -> 0.25 -> 0.22 -> 0.19 C/s) and still walked
into the guard; by the last requests the clock had dropped to 1227 MHz, so throttling had begun.
Per Codex's criterion, flattening — not duration — is the success test, and this failed it.

**Conclusion: this is a STATIC PRESSURE problem, not an airflow-volume one.** An axial chassis fan
stalls against the fin stack's backpressure. The Delta BFB1012VH is a centrifugal blower rated
~580 Pa precisely for that job, and per its datasheet P-Q curve clears NVIDIA's 12-19 CFM
through-fin requirement at realistic backpressure. **The blower is on the critical path.**

**The blower's fault is IDENTIFIED and free to fix.** User-reported wiring at the CRJ adapter:
`black -> black`, **`yellow -> grey (+12 V)`**, `blue -> nothing`, **`red -> nothing`**. Delta's code
for this part is **red = POSITIVE (+12 V)**, black = ground, yellow = tach/FG, blue = PWM. So the
motor's positive lead is dead-ended and 12 V is sitting on the tachometer line — which explains why
it never spun on the motherboard header OR on Molex. Fix = reseat the plug so **red takes the 12 V
and black takes ground**, yellow and blue unconnected (almost certainly a 180-degree flip or a
one-position shift, since black/yellow are adjacent to red/blue). Delta documents **polarity
protection** on this SKU, so the earlier miswiring should not have damaged the motor; only the FG
driver is at risk, and that costs nothing but the tach reading.

Hardware confirmed present: the "Tesla P100/P40 fan shroud" recorded as *on order* at line 835 **has
arrived and is fitted**. Blower is `7305B05P-DE` / BFB1012VH, Delta Electronics.

**Still unaddressed (Fable):** ledger **F25 records an Xid 79 at IDLE, zero load** — a possible
contact/electrical fault independent of heat. Line 1260 prescribes *reseat and brace the card, revert
the slot to Gen3*. Both happened incidentally tonight (card reseated into slot 5, now Gen3 x16), but
a good thermal run must not be read as closing that out.

card is **ALU-bound, not bandwidth-bound** (20-23% of peak; 81,883 XMAD, 0 IMAD, 0 IDP4A — GP100
has no native 32-bit integer multiply). **Bonsai's advantage is fewer BYTES; the P100's bottleneck
is ARITHMETIC**, and ternary decode costs MORE arithmetic per weight (PTQ1_0 unpack + a Hadamard
rotation over 402 tensors) on precisely the hardware worst at integer math. Bonsai is the right
model for a bandwidth-bound card that cannot hold Ridge. The P100 is neither.

| A2 | PTQ1_0 | 8.505 | 117.58 | 7181 MiB | 3.1 s |
| **B2** | **PQ2_0** | **17.521** | **57.07** | 8325 MiB | 3.1 s |

**PTQ1_0 mean 8.506 -> PQ2_0 mean 17.565 t/s = +106.5%.** Output is **BYTE-IDENTICAL** at 64
tokens, and prefill is unchanged (1081.8 vs 1091.9 ms), so the entire gain is decode.

**Cost: +1144 MiB** (7181 -> 8325 at 32K). The 262144 context ceiling is very likely lost and needs
re-measuring — PTQ needed 15917 of 16269 MiB at 262K, so +1.14 GB does not fit.

**MECHANISM (corrected by Codex — my first explanation was incomplete).** Section 15's trace put
`mul_mat_vec_q` at 89.8% of decode. I claimed PQ2 changes ONLY the unpacking. It changes **two**
things:

> PTQ walks base-3 packed values and consumes **128 weights per participating thread**. PQ2 uses a
> simpler two-bit codec and consumes **32 weights per participating thread**. PQ2 therefore changes
> both unpacking AND work distribution.

That second half is the bigger one. At K=5120, PTQ yields 40 work-units for 128 threads — the 31%
thread-occupancy problem identified from the shapes. **PQ2 at 32 weights/thread yields 160 units, so
every thread works.** So PQ2 incidentally fixes the very geometry defect the planned kernel build was
meant to address, which is why the measured gain is 2.07x rather than the +20-25% Codex forecast
from unpacking alone. Both formats still use the same sm_60 scalar `dp4a` fallback; PQ2 gains no
integer-dot hardware.

**Consequences:** PQ2 has **`vdr=1`, so its `small_k` threshold is K<4096, not 16384** — all three of
this model's K values (5120 / 6144 / 17408) take its ordinary four-warp, one-row path. And **do NOT
multiply a future PTQ geometry gain by the PQ2 gain**: they overlap and are alternative paths.

**Against predictions:** Codex estimated 10-40% with low confidence and explicitly warned PQ2
"does not remove the entire Pascal penalty". The measured +106.5% is far beyond that. My own
"realistic stacked ceiling ~13 t/s" was wrong, and so was the framing that ternary is structurally
mismatched to this card — **it was the PACKING, not the format.**

**Deployment consequence: Bonsai at 17.57 t/s is now level with Ridge's 18-20** while still being
the model with a far larger context ceiling. The "Ridge for speed, Bonsai for context" split from
section 11 is superseded.

**REPACK VERIFIED structurally (GGUF header comparison, 2026-09-21):**

```
tensors           851 both, identical name set, ZERO shape mismatches
type transitions  402 tensors  143 (PTQ1_0) -> 142 (PQ2_0)
                  353 stay F32, 96 stay type 30   -- unchanged
Hadamard metadata ALL 10 keys IDENTICAL, incl. the 401-entry weight_names
                  list and the 28,672-entry sign_values array
KV differences    0  (excluding file_type / quantization_version)
```

**Only the 402 ternary tensors were re-encoded.** Shapes, non-ternary tensors and the entire
Hadamard rotation metadata are bit-identical. This rules out the worrying alternative — that PQ2 is
a *differently quantized* model that merely agreed for 64 tokens. The size delta is exactly
1,259,520,000 bytes = **6 extra bytes per quantized block**, consistent with a repack.
(402 vs Codex's 401: the extra is `token_embd`, quantized but not Hadamard-rotated, which is why
`weight_names` has 401 entries.)

**NOT absolute proof:** confirming the decoded ternary VALUES match would require dequantizing both
and comparing tensor by tensor. Combined with byte-identical generated output this is a practical
standard, not a numerical one.

**PQ2 CONTEXT CEILING MEASURED: 229,376 tokens** (15,813 MiB, 456 MiB spare). 245,760 fails with

196K=14565 / **229K=15813** / 245K=FAIL. So the full trade is **-12.5% context for +107% speed**,
and 229K still dwarfs anything Ridge can hold.

### 17. ⚠️ DO NOT USE ngram-simple WITH PQ2_0 — it HALVES throughput

**Measured, copy-heavy payload (ngram's best case), matched 49 C starts, same launcher:**

| arm | t/s |
|---|---|
| PQ2_0, spec off | 17.62 / 17.57 / 17.53 |
| **PQ2_0 + ngram-simple** | **8.41 / 8.46** |

**-52%.** **MECHANISM (Codex, and my first reading was too strong):** `ngram-simple` **defaults to
48 draft tokens** — controlled by `--spec-ngram-simple-size-m`, NOT `--spec-draft-n-max` — which
can produce a **49-token verification batch**. **MMVQ's batch limit is 8** (`mmvq.cuh:3`); above it
both formats fall through to a **cuBLAS path that EXPANDS the weights before multiplying**
(`ggml-cuda.cu:1448/1863`), bypassing PQ2's advantage entirely. PTQ's MMQ path needs Turing MMA and
PQ2's is rejected below the compiled DP4A threshold, so neither rescues it.
**My "it is not merely draft overhead" was stronger than the evidence permits** — actual
verification widths, acceptance and rollback time were never measured. Note too that PTQ+ngram ran
~100 ms/token while PQ2+ngram runs ~118 ms: **absolutely slower**, which halving the baseline's
overhead budget does not explain.
**LEVER TESTED AND IT CONFIRMS THE MECHANISM.** `NGRAM_M=2` (`--spec-ngram-simple-size-m 2`),
same copy-heavy payload, cold 37 C start:

| arm | t/s |
|---|---|
| PQ2, spec off | 17.62 / 17.57 / 17.53 (mean 17.57) |
| PQ2 + ngram, default size-m (48) | 8.41 / 8.46 / 8.46 |
| **PQ2 + ngram, size-m 2** | **17.75 / 17.63 / 17.60 (mean 17.66)** |

**Capping the draft width fully removes the -52% collapse** — which proves it was the default's
48 draft tokens overflowing MMVQ's batch limit of 8 into the weight-expanding cuBLAS path, exactly
as Codex diagnosed. **It is a configuration bug, not a PQ2 defect.**

But at **+0.5% over baseline it is within noise**: speculation does not earn its keep on PQ2 the way
it did on PTQ (+17.3%), because PQ2's target step is half as long and leaves far less room for
drafting to pay for itself. **Default stays speculation OFF.** The value of this test is the
explanation, not a gain.

**This falsifies my own recommendation.** I measured ngram at +17.3% on PTQ1_0 and wrote that it
"never hurts — worst case = baseline", recommending it as a default. Codex flagged that as
overstated ("rejected drafts and searching can cost time on other prompts"). It was right, and the
magnitude is far worse than a small cost.

**RULES:**
- **PQ2_0 (the default): speculation OFF.** `--spec-type` unset.
- ngram-simple's +17.3% applies ONLY to the slow PTQ1_0 path it was measured on, and PQ2 beats
  PTQ+ngram (17.57 vs ~10.0) by a wide margin anyway, so there is no configuration where ngram wins.
- The two optimisations are **mutually exclusive, not additive**.
- Codex's general warning stands: speculation wins only when `(T_B + D)/tau < ms/token`, and
  **halving the target step time (117.56 -> 56.79) halves the room available for draft overhead.**
  Re-measure speculation from scratch after ANY change that moves the baseline.

## 1. The boot problem — SOLVED (theory), fix untested

### The mechanism

The variable is **not electrical**. It is what the BIOS has **cached in its PCIe device
inventory**, and that NVRAM survives being unplugged.

| cached inventory before the boot | POST path | result |
|---|---|---|
| no GPU | card is a NEW device → full enumeration, fresh BAR allocation | **works** |
| GPU already listed | fast path, reuses cached config | **hangs** |

The ritual works because the no-GPU boot is the only thing that **erases the card from the
cache** — it makes the card new again. It is *not* clearing a corrupt entry.

Why this card specifically: the P100 needs a **16 GB prefetchable BAR**
(`Region 1: Memory at 380000000000 (64-bit, prefetchable) [size=16G]`) — exactly what a
cached-config fast path on a 2015-era workstation BIOS is most likely to get wrong.

This explains **every** observation, including the two that killed earlier theories:
days-unplugged still hangs (NVRAM persists), and reboot-after-success still hangs.

### Theories tried and killed — do not re-run these

| theory | killed by |
|---|---|
| thermal damage | card reports 0 ECC, full 16 GB, healthy after |
| warm vs cold restart | full wall unplug + drain with 8-pin in still hung |
| total time de-energized | days unplugged still hung (288 s dry) |
| marginal 8-pin seating | reseat hung |
| B5/B6 SMBus tape | 8-pin-out boots work 100% with tape unchanged |
| stale/corrupt ESCD entry | reboot after a *successful* boot also hangs |
| aux-rail sequencing race (Fable) | predicts a coin flip; behaviour is deterministic |
| D3cold resume failure | real and reproducible, but doesn't explain days-unplugged |

**D3cold is still a genuine, separately reproduced fault** — see §1.2 — it just isn't the
boot mechanism.

### 1.2 D3cold, reproduced on demand (2026-08-28)

With the machine up and the GPU idle, stopping `nvidia-persistenced` and
`modprobe -r nvidia nvidia_uvm nvidia_drm nvidia_modeset` produced:

```
nvidia 0000:02:00.0: Unable to change power state from D3cold to D0, device inaccessible
nvidia 0000:02:00.0: probe with driver nvidia failed with error -1
lspci -vv: !!! Unknown header type 7f
```

`power/control=on` + PCI `remove` + `rescan` did **not** recover it; after the rescan the device
was gone from the bus entirely. This is the same `header type 7f` signature seen at POST, which
is why it looked like the same bug. Only a full power cycle recovers the card.

### Fixes, cheapest first — ALL UNTESTED

1. ~~**Disable Fast Boot / Quick Boot**~~ — **DEAD. `Fast Boot` was read over SSH on 2026-08-28
   and is ALREADY `Disable`.** Full re-enumeration is therefore already forced every POST and the
   box still hangs, so the cached-inventory mechanism loses its main support. Do not re-run this.
   **New lead: `MMIO Assignment Mode` = `Auto`** (`32 Bit`/`64 Bit`/`Auto`) — HP's Above-4G
   equivalent, governing exactly the P100's 16 GB prefetchable BAR. Set it to `64 Bit`.
   **Second lead: `Slot 2 Limit PCIe Speed` = `Gen1 (2.5Gbps)`** while every other slot is `Auto`,
   and BIOS Slot 2 maps to `0000:02:00` — the P100's own address. Set `Auto`. Change ONE at a time.
2. **Confirm Above 4G Decoding / large MMIO is enabled**, or the 16 GB BAR has nowhere to go.
3. **BIOS update** — large-BAR handling improved across Z640 revisions.
4. **Load BIOS defaults once** to scrub the cached entry.

**Sharp, cheap test:** with Fast Boot off, a straight reboot with the 8-pin IN should succeed.
One reboot settles it. If it still hangs, the cached-config path is wrong and the serial console
finally earns its place.

### BLACK SCREEN ON THE QUADRO — ROOT CAUSE, corrected 2026-08-30

**`Configure Option ROM Launch Policy = All UEFI`.** The Quadro 600 is Fermi GF108 (2010) and its
VBIOS is **legacy-only, with no UEFI GOP driver**. Under an `All UEFI` policy the firmware refuses
to launch it, so the card never paints POST video — **in any slot** — while Linux drives it

### 2026-08-29: LONG-CONTEXT PREFILL IS NOT USABLE WITHOUT THE SHROUD

Feeding a real **13,492-token** prompt (Ridge, 32K, turbo4) took the card from a 61 C idle to the

Also note the card boosts to 1328 MHz for ~2 s, then settles to 1189 MHz power-capped at 150 W.

### 125 W power cap TESTED 2026-08-29 — NOT a substitute for cooling

`nvidia-smi -pl 125` (**125 W is the hardware floor**; default 250 W, was capped at 150 W by

|---|---|---|---|

## 3. Performance — the "why only ~12 t/s" investigation, SETTLED

### Bottom line

**The P100 is performing normally. There was never a missing 5×.** It is **compute-bound**, not
bandwidth-bound, so its 732 GB/s — 2× the RTX 3060's — is roughly 4× more than llama.cpp decode
can consume at these quant levels. The "58 t/s theoretical" that started this
(732 GB/s ÷ 12.6 GB) was never reachable.

The decisive comparison — effective bandwidth (model size × t/s):

| format | P100 | RTX 3060 |
|---|---|---|
| IQ4_XS | 172 GB/s | 199 GB/s |
| IQ2_S-heavy | 134 GB/s | 138 GB/s |

The P100 tracks the 3060 to within a few percent on both, despite double the memory bandwidth.
That ratio is roughly its FP32 ratio (9.5 vs 12.7 TFLOPS) plus a small dp4a penalty.

### dp4a is a red herring — measured, not argued

Built the same tree twice for sm_86, one with a new `GGML_CUDA_NO_DP4A` macro forcing the exact
scalar fallback sm_60 is stuck with. Verified at SASS level: **11,840 `IDP.4A.S8.S8` → 0**, with
IMAD 8,062 → 22,862 and ~17k new `SHF.R.*.HI`. So ~3 extra instructions per dp4a, not the ~8
assumed — nvcc vectorizes the sign-extend, which also means a hand-written PTX IMAD emulation has
almost nothing to recover.

Decode on the 3060, `Qwen3.8-4B` (same `qwen35` hybrid arch), all formats quantized locally from
one BF16 so provenance is identical:

| quant | GB | dp4a | emulated | slowdown | eff GB/s |
|---|---|---|---|---|---|
| Q4_0 | 2.61 | 78.62 | 73.78 | 1.07× | 205 |
| Q4_K_M | 2.78 | 72.21 | 65.55 | 1.10× | 201 |
| IQ4_XS | 2.58 | 77.21 | 75.35 | 1.02× | 199 |
| IQ3_S | 2.19 | 72.87 | 72.05 | 1.01× | 160 |
| IQ2_S | 1.72 | 79.99 | 74.66 | 1.07× | 138 |
| Q3_K_S | 2.14 | 55.0 | — | — | **118** |

**Losing dp4a costs 1.01–1.10×** — it hides behind memory latency, and i-quants are the *least*
affected. **No kernel work is justified.**

### The real axis is bit-width, not i-quant vs K-quant

The size-matched control inverted the first reading: **Q3_K_S (2.14 GB) is *slower* than IQ3_S
(2.19 GB)** — 55.0 vs 72.9 t/s, reproducible over 3 runs. So there is no "i-quant compute
ceiling". Every 4-bit format (Q4_0, Q4_K_M, IQ4_XS alike) lands near 200 GB/s-equivalent, and
everything below 4 bits degrades, with **Q3_K_S the worst of all**.

**Do NOT "fix" this by switching to a K-quant.** And do not trust the "K" in Unsloth's
`UD-Q3_K_XL` — that file is i-quant heavy despite the label.

### On the P100 itself (llama-bench, `-p 0 -n 128 -r 2`, turbo4 KV, no MTP either side)

**The 11.79 t/s baseline was MTP-inflated:** Ridge is 10.62 without it, so MTP is worth ~+11%.

## 5. Gotchas that cost time — don't rediscover these

- **`llama-bench --output csv` has no `tg128` field.** The test is encoded as `n_prompt`/`n_gen`
  columns; throughput is the **second-to-last field of the last row** (`avg_ts`).
- **`curl` does not fail on HTTP errors without `-f`.** A llama-server readiness loop will treat
  a 503 "Loading model" as success and fire the request while the model is still loading. Poll
  the body for `"status":"ok"`.
- **`pkill -f` matches the remote shell running your own command string.** Use the bracket trick
  (`[l]lama-bench`). This silently killed SSH sessions twice.
- **ARP cache gives false "host is up".** Flush with `ip neigh flush all`, exclude `FAILED`
  entries, and require a real ping reply.
- **imatrix from a quantized model produces fused `attn_qkv` names** that won't match a BF16
  requantize. And the **last block is the MTP/`nextn` head**, never run in a forward pass, so
  imatrix can never cover it — pass `--tensor-type "blk.<N>=q4_K"` or IQ2_S quantization aborts.
- **BF16 imatrix OOMs** at `-ngl 99` and even `-ngl 14` alongside a running local.
- **`hf` CLI is not on the Z640**, and `python -m huggingface_hub.commands.huggingface_cli` does
  not exist in the installed version — use `from huggingface_hub import hf_hub_download`.
- **Xet downloads hang** on this connection (documented failure: dead at 0 bytes/s with the
  process alive). Fall back to `aria2c -x12 -s12 -j8 -c`, which writes to the **final filename**
  so a truncated file looks complete — always verify byte size against the HF metadata.
- **`~/lucebin` has only `llama-server`.** `llama-bench`/`llama-quantize`/`llama-imatrix` live in
  `~/lucebench` (copied from the ARCHS=600,860 `build/`).

### NIGHT OF 2026-08-30/31 — the draft-depth win, the 96K unlock, and the speculation ceiling

**HEADLINE: two defaults were costing us most of the available performance.**

**1. `--spec-draft-n-max` default 3 -> use 1.** IQ4_XS @8K: **16.67 t/s** at depth 1 (77.5% acceptance)
vs 14.14 at depth 3. Monotonic, no middle optimum. **16K now fits too (16.23 t/s)** - the old 16K OOM
was never about context, it was a deeper draft's KV. 32K still OOMs: **16K is IQ4_XS's ceiling.**

**2. The MTP draft KV was F16 while the target ran turbo4.** `common_params_speculative_draft::cache_type_k/v`
defaults to `GGML_TYPE_F16` and we had never set it, so every MTP run all week carried an uncompressed
draft cache. **`-ctkd turbo4 -ctvd turbo4` saved 230 MiB and unlocked Ridge at 96K: 15703 MiB, 15.12 t/s,
100% acceptance.** Ridge ladder at depth 1 is essentially flat in speed: 64K 15.20, 80K 15.16, 96K 15.12;
128K crashes at load.

**WHY DEPTH 1 WINS - the economics, measured.** One plain token = 83.1 ms. A depth-1 round = 106.5 ms for
1.775 tokens. Marginal cost per extra draft position is roughly constant (+23.4, +36.9, +36.8, +20.9 ms)
while marginal acceptance collapses (+0.775, +0.505, +0.268, -0.106). **Break-even marginal acceptance =
0.282**; only the first draft clears it comfortably.

**WHERE THE TIME GOES** (from the `dur(b,g,a)` statistics field; `g` = time inside `draft()`):
target verify 1st position **83.1 ms (78%)**, 2nd position **16.4 ms (15%)**, the MTP head itself
**7.0 ms (6.6%)**. So verification **amortises well** (2nd position costs only 20% of the 1st - that is why
the first draft pays 2.8:1) and **the MTP head is not the bottleneck**: optimising it to zero caps at +7%.

**THE CEILING.** Round time barely depends on acceptance, so 90% -> 17.84, 95% -> 18.31, **100% -> 18.78 t/s
(+12.7%)**. Free drafting *and* perfect acceptance = ~20.1 t/s (+20%) absolute. **The bottleneck is
verification compute, not acceptance.** And deeper drafting cannot be rescued: `qwen35.cpp` asserts
`n_layer_nextn == 1` and the draft loop calls `llama_decode` once per drafted token, so **drafting is
inherently sequential** - a one-block MTP head cannot emit two tokens per forward. That is precisely what
DFlash's block-diffusion drafter removes, and precisely why it needs a different, trained drafter.
**VERDICT: depth 1 is near-optimal on this card. The remaining prize is context/VRAM, not t/s.**

**DFlash investigated and RULED OUT for this box** (source/issue-level, not paper-level): it requires
**non-causal cross-attention**, and vLLM issue #41559 records that `TURBOQUANT` has `causal=True`
**hardcoded with no non-causal path**, FlashInfer/Triton reject non-causal outright, and FlashAttention
rejects quantized KV when non-causal. Adopting it means losing turbo4 - which would take Ridge from 96K to
roughly 21K. It also needs FlashInfer/TRT-LLM kernels absent on sm_60, and a trained `DFlashQwen3ForCausalLM`

**MTP DRAFT-KV WINDOW - new feature, commit `e56e140b8`, `build-sm60/` -> `~/lucewin/` on the Z640.**
`LUCE_MTP_WINDOW=<tokens>` caps the drafter's KV independently of the target's (the MTP context otherwise
inherits the target's full `n_ctx`). Measured at 96K target, copy task:

| window | VRAM | prefill t/s | decode t/s | drafts | accepted | acceptance |
|---|---|---|---|---|---|---|
| full | 15703 MiB | 124.75 | 15.14 | 39 | 39 | 100% |
| 1024 | 15551 MiB | 125.05 | 15.18 | 39 | 39 | 100% |
| 512 | 15551 MiB | 124.91 | 14.80 | 40 | 39 | 97.5% |

The copied source sits **549 tokens back** - inside 1024, **outside 512** - yet acceptance only drops to
97.5%. Carefully stated: **the MTP head does not NEED that 549-token-old KV cell**; the information is
available via `h_tgt` and/or nearby MTP state. Prefill is unaffected, so windowing is a memory effect only.
**The saving is ~152 MiB at a 96K target, but it SCALES with context and is load-bearing at 128K.**
(An earlier note in this section saying "windowing does not reach 128K" was written from the 96K figure and
is retracted.) The real 128K blocker was the **compute buffer: 990.95 MiB**, and `-b/-ub 256` shrinks it
enough. Proof the window matters: stock `lucebin` at 128K (no window, F16 draft KV) loads 16129 MiB with
255 free and **OOMs at generation**; patched + `-ctkd turbo4` + `LUCE_MTP_WINDOW=1024` loads **15619 MiB
and runs**.

**128K CONFIRMED WORKING (2026-08-31):** `-c 131072 -b 256 -ub 256 --ctx-checkpoints 1 -ctkd turbo4

### 22.2 Delta BFB1012VH — specification

97 x 95 x 33 mm, 12 V, 1.5-1.8 A (18-21.6 W), 38-43 CFM, **~580 Pa static pressure**,
4500-5000 RPM, ~56 dBA, **4 wires: red / black / yellow / blue**, moulded connector
(conductors cannot be separated without cutting).

NVIDIA's through-fin requirement for a passive P100 is 12-19 CFM **at the fin stack**
(15 CFM at 35 C inlet, 19 at 40 C) — a through-fin figure, not a catalogue free-air figure.
Per its datasheet P-Q curve the BFB1012VH clears that at realistic backpressure. That is the
whole reason this part is on the critical path: an axial case fan stalls against the fin stack,
a centrifugal blower does not.

### 22.3 THE WIRING FAULT — diagnosed, free to fix, NOT yet done

User-reported wiring as found at the CRJ adapter:

```
blower   ->  adapter
black    ->  black
yellow   ->  grey (+12 V)     <-- 12 V sitting on the TACH line
blue     ->  nothing
red      ->  nothing          <-- motor positive DEAD-ENDED
```

Delta's colour code for this SKU:

```
red    = POSITIVE (+12 V)
black  = ground
yellow = tach / FG
blue   = PWM
```

So the motor's supply lead was never connected and 12 V was being fed to the tachometer output.
**This explains every "it never spun" observation** — on the motherboard front fan header, and on
the 4-pin Molex ("D3", the harness feeding the optical drive) through a Molex-to-3-pin adapter.
Neither test was a fair test of the blower.

**Fix: reseat the plug so red takes +12 V and black takes ground; leave yellow and blue
unconnected.** Almost certainly a 180-degree flip or a one-position shift of the connector, since
black/yellow sit adjacent to red/blue.

Delta documents **polarity protection** on this SKU, so the miswiring should not have killed the
motor. Only the FG (tach) driver is at risk, and losing it costs nothing but the RPM reading —
the blower does not need to report a tach to anything.

**Before declaring it dead after rewiring:** check the impeller spins freely by hand, and measure
voltage **at the blower** while it is connected, not at the source.

**Also true and independently important:** a stationary blower taped over the heatsink is
**worse than no blower** — it blocks the inlet. It is currently held on with aluminium/duct tape.
